A new opt-in rule, `status.children-agreement`, holds a record's status to the records that are part of it (the type's `pointer_fields` entry declared `part_of: true`). Enable it with `status.children-agreement: error` under `rules:`; it has no options, and a repository that does not enable it sees no finding and no notice. On the parent's file it reports a parent that is not started (a status outside its type's `statuses.progress`) while a child is under way or finished, and a parent that is finished (`statuses.success`) while a child is neither finished nor dropped; the message names the parent, its status, the children by state and up to five of the children that make it disagree. These are the two cases `state_disagrees_with_children` in `urzua export` already flags. A parent whose children are all finished and that is still under way is not reported, nor is a dropped parent, a parent of a type with no `statuses.progress` (unless finished), or a record whose `part_of` field names several records. Where the parent's type declares exactly one progress status, its transitions lead there and no `authority` gate reserves the move, the finding's suggested action sets the parent's `Status` to it; a gated move is never suggested and the finding names who may make it. `urzua fix` does not apply it. Under `check --base`, a child the change added, or whose `Status` or `part_of` value differs from the merge base's, brings its parent into the run, so the finding appears on the pull request that caused it. Enabled with no `part_of` field, or with a parent type that declares no `statuses.progress`, `check` says so in one notice. The agent harness says it at the moment a child changes: the post-command report adds one line per parent when a command changed a child that contradicts it ("PARENT is still 'Planned' while CHILD is now 'Active'") and gains a `parent_state` list only when there is such a line, and the editor hook's allowed-edit message carries the same line for a proposed child, without blocking.
