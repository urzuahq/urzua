`urzua fix --conflicts` now resolves a record where one branch replaced a pinned locator (narrowed `code:path`, the whole file, to `code:path#symbol` or a line range) and the other branch only re-pinned the old one. It used to refuse these when the locator was in a Done means item, and keep the narrowing side's hash unchecked when it was in `Realized-by`. The changed locator wins in both places, its pin is recomputed from the merged file, and the merge revision row names the locator it replaced. A locator both branches replaced with different ones is still refused, naming both. Replacing a range or symbol with another scope, widening, or moving a locator to another file is refused with the reason, because the other branch's re-pin does not cover the new span. A pin over a range or symbol is recomputed on merge only when each side that pinned it left the file as in the base outside it and, for a range, the merge kept the lines above it; before, a merge could pin lines another branch had edited or shifted into the range. The rule is stricter than shifting alone: an edit above a range by the other branch refuses the record even when no line moves, and where both branches re-pinned one range or symbol, a merge that combines their changes across its edge (two deletions inside one range, say) is refused too. A new locator that could replace more than one dropped locator of the same file is refused, since the pairing would depend on the order written.
