# SPEC-24 — The harness request, verdict and adapter layout

## Purpose

The complete reference for what `ADR-89` (section 6) calls the vendor-neutral contract of the agent
harness: the request and verdict that `urzua harness run <event>` reads and prints, the layout of an
adapter directory in the bundle embedded in the binary, and `.urzua/harness.lock`. The engine names no
agent vendor; an adapter is the only part that does, and it is written against this contract. The
configuration keys (`harness`, `authority`) are in `SPEC-3`; the commands are in `SPEC-3` and `SPEC-19`.

## The request

`urzua harness run edit`, `urzua harness run session-start` and `urzua harness run post-command` read one JSON object from stdin. An
unreadable one is not a crash: for `edit` and `post-command` it is a stated verdict (below). `session-start`
needs nothing from the request but `cwd`, so an unreadable one is read as an empty request and the check runs
in the current directory.

| Field | Type | Meaning |
|---|---|---|
| `event` | string | `edit`, `session-start` or `post-command`. Informational: the subcommand decides, and the engine does not read it. |
| `tool` | string or null | The agent's tool name, informational; the engine does not read it. |
| `paths` | list of strings | `edit` requires exactly one path, absolute or relative to `cwd`. A request that names several is malformed. A person's is judged as before: under `on_unjudged: allow` it is allowed unjudged (refused by neither gate), whatever the paths, and under `on_unjudged: deny` it is refused as before. An agent's runs the `acceptance` and `protected-paths` gates on every path, and a block on any path wins. With `on_unjudged: allow` an agent's request that no gate blocks is refused only when a guardrail set to `on_unjudged: deny` covers a named path, and otherwise is allowed unjudged as before; with `on_unjudged: deny` it is refused as before. More than 512 paths (`harness.limits.paths_per_call`, `SPEC-3`, which may raise it but never lower it) are not all judged, because each costs a search for the repositories that hold it: the first that many are judged as above, and the rest are an edit that was not judged, which an agent's request has refused when a guardrail set to `on_unjudged: deny` covers one of them (the message names the cap) and otherwise is allowed unjudged, as the translator treats a call of more files than the same cap. `post-command` reads none: git names the changed paths. |
| `content` | string or null | `edit`: the full proposed content of the file. The adapter computes it from the agent's edit. |
| `contents` | list of string or null, default empty | `edit` with `gates_only` naming several paths: the proposed content of each path, parallel to `paths`. A path without an entry, or with a null one, is judged with `content`, and with no `content` by its path alone (a protected path still blocks). A `contents` list whose length is neither 0 nor the number of `paths` is an adapter error: the request is not judged, and a guardrail set to `on_unjudged: deny` that covers a path refuses it. The `acceptance` gate and the outside-writes judgement read the entry of the path they judge. |
| `actor` | `agent` or `human` | Who is acting. Absent, or any value but `human`, means `agent`. Only `on_unjudged: deny` and the `authority` gates read it. |
| `cwd` | string or null | The directory the engine enters before it finds the repository. The edit is judged against the session's repository (the one that holds `project_dir`, else `cwd`) and against every governed repository, a git working tree that git accepts with `.urzua/config.yaml`, that holds the file the edit writes (symlinks followed), inner or outer; a block from any of them is the verdict, and a repository the session did not start in can add restrictions and never remove them. With `harness.outside_writes: shared`, a file whose git toplevel shares the session repository's `git rev-parse --git-common-dir` (a linked worktree) is also judged by its path relative to that toplevel against the session's own acceptance and protected-path gates, a block winning, and a record's status before the edit is the one in that worktree, not the session's copy; with `deny`, an agent's write outside the session's repository is blocked unless it is under `harness.allow_paths` (`SPEC-3`). A `cwd` outside the repository, or inside a nested repository that has no configuration of its own, still finds the governed one. A write that the harness allows and whose every path, as written and as its symlinks resolve, lies outside the repository judging it is `allow` with an empty message, so the translator prints nothing, unless `harness.report_outside_writes` is `true`, which restores the `allow-unjudged` notice ("is outside the repository"). This is not a silent no-op of urzua's (`SPEC-1`): urzua governs the files of its repository, a file outside it is no file urzua was asked to judge, and nothing that is refused (`outside_writes: deny`, under `shared`, a gated move or protected path in a linked worktree, the editor hook's `on_unjudged: deny` for an agent) or unjudged inside the repository becomes silent. A relative path is made absolute against `cwd` first. A `cwd` that cannot be entered (gone, not a directory, not readable) is replaced by `project_dir` when that can be entered, and the relative paths are then made absolute against it; with neither, no repository can be found and the call is unjudged as an unreadable request is (below). |
| `project_dir` | string or null | The directory the session started in, which the Claude Code adapter (`urzua harness hook claude-code`) takes from `CLAUDE_PROJECT_DIR` when that holds `.urzua/config.yaml`, and, when the variable is unset, from the nearest git working tree at or above its working directory that holds one. `edit`, `session-start` and `post-command` enter its repository first. Absent: `cwd` stands in; a `cwd` that cannot be entered is replaced by it. |
| `adapter_error` | string or absent | `edit`: set by a translator that could not build a request (an unreadable payload, an edit it could not place). The engine builds no judgement from it. With no `paths` (an unreadable payload) it refuses the call for an agent when `acceptance` or `protected-paths` is enabled with `on_unjudged: deny` (read from the raw configuration). With a path (an edit the translator could not place, such as an `old_string` that is not in the file) it refuses only when that path is a protected path, the configuration, or a record of a type a status gate names (matched as for the gates), judged as written and as resolved. For any other file it returns `allow-unjudged` with a message: the edit tool's own failure handles an absent `old_string`. |
| `gates_only` | boolean, default false | `edit`: judge only the `acceptance` and `protected-paths` gates, which answer in milliseconds. A gate that denies gives the usual `block`. Otherwise the verdict is `allow` with an empty message and a `record` field: `true` when the full judgement of the path would check a record (the path is one a record type governs, the `editor-hook` guardrail is off so its notice is owed, or the path cannot be placed), `false` when it would not. A request that names several paths is judged for every path (each with its `contents` entry, any block winning), and the verdict also carries `records`, a list of booleans parallel to `paths`. An adapter that has several files to judge asks this of all of them in one request, so a denial returns before any record is checked and the cost of the gates does not grow with the number of files by a process each. |
| `override` | `{name, reason}` or absent | A named override of the editor hook (`ADR-78`). The environment variables `URZUA_HOOK_OVERRIDE` and `URZUA_HOOK_REASON` mean the same when the field is absent. |

## The verdict

One JSON object on stdout with `verdict`, `message` and `findings`, and `path` (the record or file the verdict is about, absent when none) and `override` (the name of the override that was applied, on `allow-override` only) when they apply; a `gates_only` request that no gate denied also carries `record` (a boolean, see the request table). `findings` carries the findings the verdict is about (the blocked, the
overridden or the shown ones, as `urzua check` prints them); for `session-start` it carries the
readiness problems, each `{check, message}`. The session-start `check` values are `config`, `binary`,
`lock`, `version`, `adapter`, `interpreter`, `environment`, `file` (an installed file that is gone, or whose
hash differs from the lock's; the adapter's commands directory is exempt from the second, since a person may
customise a drafting command), `hook-entry` (an entry that is not wired, or whose hash differs from the
lock's), `kill-switch` (a manifest `kill_switches` key set to true in the settings file) and `git-hook`.

| `verdict` | Exit | Meaning |
|---|---|---|
| `allow` | 0 | Judged, nothing to report. The message counts the rules that ran and names the enabled rules a single record cannot be judged by. For `session-start`, the harness is installed and wired, or the guardrail is not enabled. |
| `allow-with-warnings` | 0 | Judged; warnings (or errors already on disk) are in `message`, nothing blocks. Also the first half of a reciprocal relation under `editor-hook.pending_pair: allow` (the default, `SPEC-3`): the edit's only new errors are reciprocity findings that one edit of another record satisfies, and `message` names, for each, the record, the field and value still required and the `urzua fix --apply --ids <record>` command that writes it, and says that until it is written the post-command hook reports the pair and pre-commit and CI block it. The translator relays `message` to the agent as it does for any `allow-with-warnings` verdict, so the engine writes the text and the translator is unchanged. Not when the other record is a protected path: an agent can write it neither by an edit nor by `urzua fix`, so the edit is `block` and the message says a decider must make the paired change. The printed command runs as written (no placeholder): `--by` is resolved from the verified `gh` login or `git config`. |
| `block` | 1 | An unwaived error this edit introduced (`block_on`, `SPEC-3`; a reciprocity finding counts only under `pending_pair: refuse` or beside another new error, and the message then names the `urzua fix` command that writes the other half), an unjudged edit refused by `on_unjudged: deny`, or, for an `agent` actor, a move to a status, an edit that blanks a record, strips its `Status` or moves it out of a status a gate names (a gated record leaving its gate, `ADR-89` amendment of 2026-11-14), or a write to a path the `authority` table gates (`acceptance`, `protected-paths`). The last is final: a named override is not accepted for it, the message says so, and no override-log row is written. A `human` actor is not affected. |
| `allow-unjudged` | 0 | The engine could not judge: no rule examined the record, history or configuration unreadable, the guardrail is not enabled, an unreadable request (for an agent, `block` where `acceptance` or `protected-paths` denies what it cannot judge, see below), an `adapter_error`. The message says so and the edit proceeds. |
| `allow-override` | 0 | A block was overridden by name; with `override_log` declared, one row per overridden finding is appended to it. |
| `not-governed` | 0 | No record type governs the path. |

`on_unjudged: deny` turns `allow-unjudged` into `block` for an `agent` actor and leaves it `allow-unjudged`
for a `human`; a named override does not lift it. The message names the escape hatch: a person edits
outside the agent harness (a plain editor or a terminal), where no hook runs. When the configuration does
not load, the engine reads `harness.guardrails.editor-hook` from the raw file to decide, so a broken file
does not silently turn a denying guardrail into an allowing one; a file that is not valid YAML cannot be read
and is allowed. A request the engine cannot read (not valid JSON, such as a lone surrogate escape the translator's own JSON accepts), and a request whose `cwd` cannot be entered with no usable `project_dir`, place no file in any repository, so the engine does not know what the edit touches: for an agent it is refused when `acceptance` or `protected-paths` is enabled with `on_unjudged: deny` (read from the raw configuration of the process's own directory), as an `adapter_error` with no path is, whatever the `editor-hook` guardrail says; it is refused for any file, not only a governed or protected one, because the engine cannot read which file the request names; otherwise the `editor-hook` guardrail's `on_unjudged` decides, and a person's edit is allowed unjudged.

A failure of the adapter itself fails the same way, by the same two guardrails: the Claude Code adapter
(`urzua harness hook claude-code`, in the binary) sends `adapter_error` for an unreadable payload or an edit it cannot place, and refuses the edit itself, from
the configuration's text, when the engine command cannot be run or answers with something that is not a
verdict. It does so only where `acceptance` or `protected-paths` is enabled and not set to `on_unjudged: allow`;
under any other configuration the call proceeds with a stated notice. An edit the translator cannot place is
refused only when its file is a protected path or a gated record (the table above); for any other file it
proceeds with the notice, since the edit tool fails by itself when its `old_string` is absent.

Gate matching (`acceptance`, `protected-paths`) compares paths with Unicode case folding on every filesystem (each
character upper-cased then lower-cased, so `ß` folds to `ss`; names are not Unicode-normalised), judges an edit
through a symlink as the file it resolves to, and on Unix judges an edit through a hard link (a file with another
link, found by device and inode among the files under a protected path and the directories of a gated record type)
as that protected or gated file. Off Unix a hard link is judged by its own name. A symlink is followed to the end, a link whose target does not exist yet included (the parent is resolved and the name joined, up to 40 links, `harness.limits.symlink_hops`): a write through a dangling link is a write to the file it would create. While `protected-paths` is on, the edit tools are also refused for the files the harness keeps (`.urzua/cache`, `.urzua/harness.lock`, the file `override_log` names, `.git/hooks` and `.git/config`); they are not in the `authority` table, and the override path writes the log from the engine. The engine names no agent: how an
agent's tools become a request is the adapter's.

### The post-command verdict

`urzua harness run post-command` (`ADR-78`, amendment; `MILE-202`) runs after a shell command and
reports; it never blocks and always exits 0. It does not read the command: it lists the changed files with
`git status --porcelain=v1 -z --no-renames --untracked-files=all` (modified, added and untracked files; a
deleted file is dropped from the records it checks but kept for protected paths) together with the files
that differ between the commit the last post-command check saw and `HEAD`, and the files the index tells git
to ignore (`git update-index --assume-unchanged`, `--skip-worktree`, found by `git ls-files -v`) whose content
differs from the blob the index holds, a missing assume-unchanged file included (so a command that committed its
own change is covered), keeps those a record type governs, drops those whose content hash is the one last
reported, and runs `check PATHS` once over the rest, in process, staging nothing. Its verdict carries these
extra fields:

| Field | Meaning |
|---|---|
| `findings` | The unwaived findings the checked records have now and did not have at `HEAD`, as `urzua check` prints them. |
| `gated_moves` | One line per changed record the command moved to a status the `authority` table gates, and per record it deleted while it held such a status unless a surviving record carries its `Stable-Id` and record id (a rename), with the status compared case-insensitively; one line per changed record the command moved to a status the `authority` table gates (a new record, or one whose status at `HEAD` was another), judged against that commit (`HEAD` when the command committed nothing) when `acceptance` is enabled. Reported as errors of their own, never blocked; empty when none, and reported even when `check` cannot run. |
| `protected_changes` | One line per path under an `authority` path gate that the command changed, created, deleted or committed, when `protected-paths` is enabled. Matched with Unicode case folding. Includes a file git does not show (a gitignored one): the harness keeps a content hash of every file under a protected path in `.urzua/cache/protected-hashes.json` (seeded by `session-start`, refreshed by each check) and reports a file whose hash differs, that is new or that is gone. Reported as errors of their own, never blocked, once per content hash: the same change is not reported again. |
| `pre_existing` | The unwaived findings the same record already had at `HEAD`, judged from its committed text (a record with no copy at `HEAD` has none). Listed, not new. |
| `checked` | The records `check` ran on this time. Empty when no check ran: a clean tree, no governed record changed, the guardrail is off, or every changed record's content hash was already reported. |

`allow` is a check that found nothing, or none ran (the message says which); when the protected-path hash scan
stopped at its cap, the verdict is `allow-with-warnings` with the message saying some files were not hashed,
even if no finding was made. `allow-with-warnings` lists the
findings with file, line, severity, rule and message, says that the command had already run so nothing was
prevented, and that pre-commit and CI remain the hard gate. `allow-unjudged` is stated, never a quiet pass,
for a `git` that cannot be run, a working tree git does not know, a configuration that does not load, an
unreadable request and a `check` that cannot run; the message contains "NOT judged". The memory of reported
hashes is `.urzua/cache/post-command.json` (derived; this repository's `.gitignore` ignores `.urzua/cache/`, and a repository that installs the harness adds that line to its own, since `install` does not): it keeps exactly the records and protected
paths that are changed now, so a reverted one is forgotten, and a clean tree removes it. The commit the next check
starts from is `.urzua/cache/post-command-head`, written by every check that judged and by `session-start`; when
it is absent or no longer in the history the working tree is compared with `HEAD` only. The protected hashes file also holds the protected entries and the hash of the configuration file they were read from; when the configuration is unchanged and every protected file hashes as before, a clean tree ends the check before the configuration is parsed. A path is protected when the baseline's entries or the edited configuration's gate it, so a gate the command removed still reports, and files under a removed entry are still hashed and compared. The configuration file is a change of its own whenever its hash differs from the baseline's, and a command that leaves the protected set smaller is reported as such ("the protected set shrank"); `session-start` reports the same, from the previous baseline, before it takes a new one. The baseline also keeps the status gates in force (empty with `acceptance` off): a moved record is judged against the baseline's status gates as well as the edited configuration's, so a gate the command removed or narrowed, or an `acceptance` guardrail it switched off, still reports the move it was meant to stop in `gated_moves` (the line says the gate is no longer in the configuration), and the loss itself is a `protected_changes` line ("the status gates shrank", naming each `type T to S` no longer gated); `session-start` reports it too, before the new baseline. Like a shrunk protected set it is reported once: the next baseline is taken from the weakened configuration. `session-start` also clears `.urzua/cache/post-command.json`, so a change reported in an earlier session and made again is reported again. With no baseline yet (no `session-start`), the first check records one and can report nothing for a gitignored file. The walk stops at 50 000 entries and says so. The guardrail takes no
`on_unjudged`.

A gate event is never adopted silently, however it arrived (`MILE-278`): a gated status move, a gated deletion or departure, and a protected-path change are each reported once, to the person, and then enter the baseline (the memory of reported hashes and the protected-hash baseline), so a later command does not repeat them. How loudly it is reported depends on the base comparison (`MILE-311`): each gated path is compared with the configured base ref (`harness.guardrails.post-command.base`, default `origin/HEAD`, `SPEC-3`), and matches when its working-tree mode (`120000` for a symlink, compared as its link text and never followed; `100755` for an executable file; `100644` otherwise) and the blob of its raw bytes (`git hash-object --no-filters`; no clean filter or line-ending conversion runs, so a filtered or CRLF checkout does not match, while a filter cannot forge a match) equal the entry `git ls-tree <base> -- <path>` names; the index entry (`git ls-files -s`) and `HEAD`'s tree entry must equal the base's too, and no commit the command made that the base does not contain (`git -c log.showRoot=true log --root --full-history --cc <start>..HEAD --not <base> -- <path>`, so the repository's configuration cannot hide a root commit's paths) may touch the path, so base bytes left on disk over other content in the index or a commit do not match; every git call of the comparison runs with replace refs off (`GIT_NO_REPLACE_OBJECTS=1`) and with the commit-graph, its changed-path filters and `log.showRoot` pinned (`-c core.commitGraph=false -c commitGraph.readChangedPaths=false -c log.showRoot=true`), because the judged command can write each of them in the repository, and when `refs/replace` holds any entry or a grafts file exists (a shallow clone's `shallow` file does not count) nothing matches and the report says replace refs or grafts are present; likewise, when the shallow file's content differs from the one the baseline recorded, or a commit in `<start>..HEAD` is listed in it (a hand-edited shallow file acts as a graft), nothing matches and the report says the command truncated the history (a boundary in its own commits) or that the shallow file changed (each line's leading object id read from the raw bytes), while a shallow clone whose boundary lies in the base's history still matches; a path absent from all of them matches only when the command deleted it, a path whose name git gives in bytes that are not UTF-8 never matches, and a status move matches only when its whole record file does. The agent always receives its own line (for a full match, that the changes match the base and there is nothing to do, or, against a local ref or at `base_match: error`, that a decider must make or approve them), never the person's text. A match lowers the report only when the base is a remote-tracking ref (`refs/remotes/...`); with a local ref (`HEAD`, a local branch, a tag, a commit id) the matching paths are still listed in one line, at `error`, saying the base is a local ref the agent can move, so the match proves nothing. When the comparison rule (`base`, `base_match`) the configuration sets differs from the one the baseline recorded, the command's report carries a `post-command` event at `error` ("the command changed the post-command comparison rule from X to Y"; when the configuration file is unchanged, that the baseline was edited), whether or not the configuration file is a protected path, nothing is lowered for that command, and the new rule is then recorded. When every gated change matches a remote-tracking base, the person is told one sentence at `base_match` (default `info`) that names the count, up to five of the paths and then how many more, and the ref as configured (a remote-tracking ref that names another adds the branch it points at, as `origin/HEAD (origin/main)`; any other ref is called a local ref, as `the local ref HEAD`), and says nothing needs doing (at `base_match: error` it says only that the paths match the base). A change that differs is reported at `error`, grouped under one heading per guardrail and gate so each gate is named once, and the matching ones of the same command are summarised in one line; `base_match` in the verdict lists every matching path. A command that changed the configuration file is judged by the comparison rule the baseline recorded before it (the protected hashes file keeps `base` and `base_match`), and nothing is lowered unless the configuration file itself matches that base; with no recorded rule, nothing is lowered. A base that does not resolve compares nothing, every change stays at `error`, and the report says there is no base ref to compare with. The base is a local ref the agent can move or commit to, so the comparison only lowers how loudly a change is reported, never whether; CI's `diff.decider-required` against the real remote is the guarantee. When the configuration does not load, the `NOT judged` report names the changed paths the previous baseline's protected entries cover. The reflog is written by whoever runs git, the agent included, so it chooses only whether ordinary findings are absorbed, never whether a gate event is reported. A commit is the session's own when the `HEAD` reflog (at most 200 entries) has a commit-making entry for it (`commit`, `commit (amend)`, `commit (initial)`, `commit (merge)`, `cherry-pick`, `revert`, a rebase pick), on whatever branch it was made; Ordinary findings are the one thing absorbed: a changed record that no commit of the session's own changed (it entered the repository from elsewhere, by a pull, a fetch and merge, or a checkout of another's commit), and whose content on disk is still `HEAD`'s, is not checked for rule findings, and is listed in the verdict's `adopted`; its gated move, if any, is still reported. Findings in files the session's own commits changed are never absorbed, so merging or fast-forwarding to a branch that holds them still reports them. When git cannot read the reflog every commit counts as the session's own. Two limits, the same before this change and accepted (decided by the orchestrator on 2026-11-16, pending maintainer review): a shell command that commits a change and then rewrites or deletes the post-command baseline under `.urzua/cache` can lose the report of a gated move it made; and when the baseline was never seeded (the `session-start` guardrail is off, or for the first command of a session before any check ran) a gate event committed by that first command is missed. Pre-commit and CI (`diff.decider-required`) remain the guarantee. A command that changed nothing governed prints nothing.

The verdict carries each message for one audience. `agent` is a short report for the agent: the new findings, one line each; a line saying the command made a gated move or a protected-path change that a decider must make; a note on the hash scan. `person` is set only for a gated move, a protected-path change, and a check that could not run (`allow-unjudged`); it is never the same text as `agent`. `message` keeps the full report. The Claude Code translator prints nothing for `allow`, sends `person` as `systemMessage` and `agent` as `additionalContext`, never the same text in both; a translator that could not run the engine, and the installed command's shell fallback when the translator itself cannot run, state it to the person with a short `NOT judged` line to the agent. The comparison always runs: the host's report of which files a command changed is not read, since a write by an interpreter need not appear in it.

### The session-start verdict

`urzua harness run session-start` reports whether the harness can do its job in this session, and never
blocks. Its verdict is `allow` (the harness is installed and wired, or the `session-start` guardrail is not
enabled) or `allow-with-warnings` with one `{check, message}` in `findings` for each thing that would make a
guardrail fail open or not run: a problem in the `harness` key, `urzua` not on `PATH`, a
missing `.urzua/harness.lock`, a bundle older or newer than the binary, an adapter the lock names that this
binary does not embed, a `requires.interpreters` program not on `PATH`, a `requires.env` variable that is unset,
a hook entry of the lock that is not wired in the settings file, a file of the adapter's `retired_files` still in the
repository or a settings entry that still runs one (`leftover`, with the steps that remove it by hand), and a git hook problem. A configuration that
does not load is `allow-with-warnings` with the message alone. When the `post-command`
guardrail is enabled it also records the commit and the protected-path hashes (with the comparison rule) the first post-command check of
the session starts from.

## Adapter layout

The bundle is the directory `rust/crates/urzua-cli/bundle/`, embedded in the binary at build time and
laid out so that it could also be published as a release asset without a second format:

```text
bundle/
  instructions.md                    the agent-instructions block, adapter-independent
  <adapter>/
    adapter.json                     name, description, provides, settings_file, commands_dir, kill_switches, retired_files, plugin, requires
    settings.fragment.json           the hook entries to merge into the agent's project settings
    commands/draft.md                the drafting command, rendered once per declared record type
    commands/<name>.md               a lifecycle command, installed as it is
    files/<repository-relative path> installed at the same relative path (optional; the Claude Code adapter has none)
```

`urzua harness adapters` lists one entry per adapter directory. `adapter.json`:

| Key | Meaning |
|---|---|
| `name` | Equals the directory name. |
| `provides` | The guardrails the adapter can wire (`editor-hook`, `post-command`, `session-start`, ...). A guardrail the repository turns on that no chosen adapter provides is reported at install, by `status` and by `doctor`, never skipped. |
| `commands_dir` | Where the agent looks for slash commands. Absent: the adapter installs none. The install writes `<commands_dir>/<type>.md` for every record type the configuration declares (`{{type}}` and `{{dir}}` of `commands/draft.md` filled in) and `<commands_dir>/<name>.md` for every other file of `commands/`. A record type named like one of those lifecycle commands is refused. |
| `settings_file` | The agent's project settings file the fragment is merged into. A local settings file and user-level settings are neither read nor written. |
| `kill_switches` | Keys of the settings file whose truthy value switches every hook off (`disableAllHooks`). Absent: none. `session-start` reports one that is set. |
| `retired_files` | Files an older bundle of this adapter installed and this one does not. `status` (as `problems`), `doctor` (`harness-leftover`), `install` (a notice) and `session-start` (`leftover`) name one still in the repository, and a settings entry whose command names one, with the steps that remove it by hand; nothing removes them automatically. |
| `plugin` | How the agent enables a plugin that registers the same hooks: `id` (the plugin's id in the agent's settings), `enabled_key` (the settings key mapping ids to enabled) and `settings_files` (highest precedence first; `~/` is the home directory). `status` reports `registration` from it (below). Absent: the adapter has no plugin. |
| `requires.interpreters` | Programs the adapter's hook commands need besides `urzua`; `session-start` reports one that is not on `PATH`. The Claude Code adapter needs none. |
| `requires.env` | Variables the agent sets for its hook commands; `session-start` reports one that is unset. The adapter reads them and, when unset, falls back to the nearest real git working tree at or above the current directory that holds `.urzua/config.yaml`. |

The settings fragment holds hook entries. Each command is written as `"{{hook:EVENT}}"`, which `install` and `update` replace with the command the adapter generates for that event (`urzua harness hook <adapter> <event>`, then a fallback); that text, or `urzua harness run <handler>` in an entry an older bundle wrote, is how an entry is recognised as urzua's, and an entry is keyed by event, matcher and handler. The translation lives in the binary: `urzua harness hook <adapter> <event>` reads the agent's hook payload on stdin, builds the request, runs `urzua harness run <event>` (the same binary, as its own process) with it, and prints the agent's output; it always exits 0 once it has read the payload. Nothing executable is installed and no command carries a hash (`ADR-89`, amendment of 2026-11-17). The fallback runs only when that call did not happen (urzua not on `PATH`, a release without `harness hook`, a killed process): for `edit` it fails closed: it lets the edit through only when it reads with certainty that neither `acceptance` nor `protected-paths` refuses an unjudged edit (comments stripped, whole values matched, the nearest `.urzua/config.yaml` at or above the project, in the block form `enabled: true|false` / `on_unjudged: allow|deny` or the one-line `{...}` form, with no anchor, alias, tag or flow map spanning lines anywhere); any other shape, an unreadable file, or no configuration found is a refusal that tells the person to install or upgrade urzua; `post-command` and `session-start` only report. The binary's stdout is captured and printed only when it exits 0, so a failed run never leaves part of an answer in front of the fallback's. Inside the binary, a panic, and an engine that does not answer before the hook's deadline (`hook_timeout_seconds` less 15 seconds), end in a refusal of the edit as one document; a verdict word the adapter does not know (anything but `allow`, `not-governed`, `block` and the three `allow-*` words) is an edit nobody judged. The plugin's hooks file (`plugins/<adapter>/hooks/hooks.json`) is this fragment rendered with the built-in limits except `hook_timeout_seconds` at the top of its range (600), because a plugin cannot read a repository's configuration; a test keeps the two equal but for that. With no `.urzua/config.yaml` at or above the project the repository is not governed and every hook says nothing, with or without the binary. When the engine gives no verdict the binary decides from the inputs the engine reads (`run::unjudged`): every edited path made absolute against the request's `cwd` with its links resolved, and every `.urzua/config.yaml` at or above each path (as written and as resolved) and the session's own, each parsed as YAML. A path it cannot resolve, or any configuration that is unreadable, does not parse, or has `acceptance` or `protected-paths` enabled (`enabled` other than absent, null or `false`) without `on_unjudged` exactly `allow`, or `editor-hook` enabled with `on_unjudged` other than `allow`, refuses the edit; no configuration anywhere is silent. The text fallback reads no path from the payload: it finds the configuration at or above `CLAUDE_PROJECT_DIR` and at or above the working directory, each resolved to its physical path, refusing if either is not certainly open, says nothing where there is none, lets the call through with a notice where it reads it with certainty as open, and otherwise refuses every edit and MCP call until urzua is installed or upgraded. When the same hook is registered twice (repository settings and the plugin), the agent runs both; the first process to claim a call (keyed on the hash of its payload, which carries the agent's call id) judges it and the second prints the first one's output unchanged, so a call is judged once and the two answers never differ. A payload with no call id is judged by each. The `edit` entry sets `timeout` to `"{{limit:hook_timeout_seconds}}"`, which `install` and `update` fill in from `harness.limits.hook_timeout_seconds` (`SPEC-3`; default 120 seconds, 10 to 600), so a configuration that changes it leaves the entry out of date until `update`. The default 120 is above the host's default of 60: a release build's `harness run edit` of a record took 8.8 to 12.0 seconds (mean 10.5 over five runs, on a 4-CPU machine at load average 18; 5 to 7 seconds on an idle one) and a `gates_only` request 0.05 to 0.07 seconds (one request for every file of a call, 2200 files with the protected one last taking about as long as one: before it, one request per file took 128 seconds), and the Claude Code adapter judges at most 8 record-checking files of one call, so the worst call is 8 x 12.0 = 96 seconds plus about a second of gates. A configuration that raises `harness.limits.records_per_call` raises that worst case by about 12 seconds a record, so it raises `hook_timeout_seconds` with it (at most 600, room for about 48 record checks); a host that kills the hook first fails open. A host that kills the hook at its limit fails open; that is the host's behaviour.

The Claude Code adapter judges the writes of one MCP call cheapest first and stops at the first block: every file, in one `gates_only` request that carries the path and the proposed content of each (at most 512 files), then the strings it could not place (an `adapter_error` request), then, one request each, the files whose entry in `records` was true. It reads a leading `~`, `~/`, `$HOME` or `${HOME}` in a path as the home directory (a filesystem MCP server expands it before use; `~user` is not expanded), a dictionary or list under a content key (`data`, `payload`, `value`, `body`, `contents`, `text` and the like) like any other nested value (only a string there is the content), a path used as a dictionary key (`{"files": {"<path>": "<text>"}}`, the text being the content), a `file:` URL in any case of the scheme and with one, two or three slashes, and up to 512 distinct short strings of a call; a call with more strings or nested deeper than 24 levels (it names no file the translator could place, so the refusal names the tool and not a file, and it is refused wherever a gate denies), with more than 512 files (the first 512 are judged against the gates, the rest are not judged), or with more than 8 files that are checked as records, is an edit that was not judged: refused where `acceptance` or `protected-paths` is `on_unjudged: deny` and covers a file it names (or, naming none, anywhere), allowed with a notice otherwise. These numbers, with the 4096-character path and the 65536-character string it reads, are the built-in floors of `harness.limits` (`SPEC-3`): the adapter reads the effective values of the session's configuration before it scans a call and keeps the floor for any value below it, and a raised value moves only the number. An object with two different strings under its content keys (`content` and `text`, say) is not a whole-file write, because which of them a server writes is not known: its paths are strings the translator could not place and are refused as such. The translator runs the engine in the payload's `cwd` when that is a directory it can enter, else in its project directory, and sends the same as the request's `cwd`; the configuration-text fallback reads both. The gates have already run on every file by then. An engine that does not know `gates_only` judges the file in full and the answer has no `record`, which the translator takes as that judgement; an engine that answers `record` without `records` does not read a batch, and the translator asks it one file at a time. A command for an `edit` event that cannot run the translator may instead refuse the edit, reading `.urzua/config.yaml` as text, where `acceptance` or `protected-paths` is enabled and not set to `on_unjudged: allow`.

## The lock

`.urzua/harness.lock` is JSON, written in a stable order with a trailing newline:

| Key | Meaning |
|---|---|
| `schema` | `1`. |
| `bundle_version` | The engine version that wrote it; the bundle is versioned with the engine. |
| `adapters` | The adapters installed. |
| `files` | Path to `words-sha256:<hex>` of each whole file the install owns: the hash of what it says, with what a formatter changes left out. Prose counts by its words (every run of letters and digits, a list marker at the start of a line left out), so re-indenting, reflowing or changing list markers does not change it and a changed word does. Code counts exactly: every line inside a code fence (apart from its indentation and trailing spaces) and every inline code span (apart from runs of whitespace inside it), so a changed command, `&&` for `||` or a `#` that comments a step out, is a change. Prose tolerates only a closed list of formatter differences (whitespace and wrapping, blank lines, indentation, list markers and ordered numbering, the emphasis marker, table padding, trailing whitespace); any other character added, removed or changed counts. A lock written before reads `sha256:<hex>` of the exact text, which still matches. |
| `entries` | Each merged hook entry: `file`, `event`, `matcher` (absent for none), `handler` and the `hash` (`sha256:<hex>`) of its compact JSON. |
| `blocks` | Each instructions file as `file` and the `hash` (`words-sha256:<hex>`, as for `files`) of the block between its markers, markers included. |

The lock is read as JSON, so a formatter that rewrites it (re-indents it, changes its line endings) changes nothing `status` compares. An entry's hash is of its compact JSON, so re-indenting the settings file does not change it either.

`status` compares the lock with the repository and this binary: a path or entry that is gone is `missing`,
one whose hash differs from the lock's is `modified`, one that matches the lock but not this binary's
bundle is `out-of-date`. It also puts a `kill_switches` key set to true in the settings file among its `problems` (and so reports `drift`), as `session-start` does, and compares the lock's `bundle_version` with this binary's as dotted numbers (`0.10.0` is newer than `0.9.0`). `update` rewrites an item whose hash still matches the lock and leaves (and
reports) a modified one unless `--force`; it keeps the old hash for what it left, so `status` keeps
reporting it. `status` also reports `registration`, per adapter: `in_effect` is `repository-settings` (the settings file holds urzua's entries), `plugin` (a settings file the adapter's `plugin` names enables it), `both` or `none`, with `plugin_enabled_in` and a `note`; a plugin enabled in a settings file may still not be installed on the machine, which the binary cannot read, and the note says so. `uninstall` removes what matches the lock, takes only urzua's entries and the marked block
out of the shared files, and deletes the lock last.

## What's deliberately not built

- A guardrail no adapter provides. `harness.guardrails` may name one that the chosen adapters do not list in
  `provides`; the install, `status` and `doctor` report it, and nothing skips it silently.
- A published bundle (`ADR-89` option C). The layout keeps it open.
