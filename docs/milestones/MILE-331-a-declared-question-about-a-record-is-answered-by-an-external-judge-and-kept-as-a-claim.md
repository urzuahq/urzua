# 331 — A declared question about a record is answered by an external judge and kept as a claim

## What

Let a configuration declare a question about a record's meaning, have a separate command put it to an external judge the configuration names, and keep the answer in the record's evidence as a claim that goes stale when its input changes. Advisory, off by default, first in shadow.

## Why

The engine verifies a record's structure and relationships: fields exist, a state is allowed, a reference names a real record of the right type. It cannot verify that the prose supports what the structure claims. On 2026-11-17 an agent in an adopting repository was about to move a record to its finished state; two of that record's three acceptance checks, written as prose in its body and not as a declared checklist, asked for runs that had not been done; `urzua check` would have passed, because the state was allowed and the evidence section existed. In the agent's words: "We have the record that's verifiable, but is what we're verifying even making sense?" Every header field is a claim the body should support: a state, a reference to a parent, a declared dependency, a field's value.

Hosted decision models answer a fixed yes-or-no, choice or score question about a supplied text with a probability, cheaply and in about a second by their documentation. Three were examined from their own documentation on 2026-11-17, the three the maintainer named as the ones to integrate with: SubQ Snap (Subquadratic), Jev (TypeSafe) and Levanto Sage. All three accept one common request shape (a supplied text, and named questions each with a type and instructions) and return a probability per question, the resolved model version and token usage. They differ in input limit (SubQ 384 thousand tokens; Jev 64 thousand per request and 32 thousand per question; Levanto about 32 thousand), questions per call, whether an abstention is returned (Levanto only), and data retention (per each service's documentation on 2026-11-17: SubQ deletes within 60 days, with zero retention on request; Jev offers zero retention to enterprise customers; Levanto states nothing). None documents a seed.

Jev's own measurements show the same request varying between calls. For SubQ, the adopting agent replayed 58 inputs twice on 2026-11-17 with a pinned model and got the identical probability on all 58; an earlier report from that agent of 0.71 and 0.85 for one prompt was withdrawn, because the two inputs had differed. So repeatability differs by service and is measured, not assumed. What holds for all of them is that an answer can be wrong, and how often depends on the question: in the same replay one question gave 4 false alarms in 46 and 5 misses in 12 at a 0.7 threshold while another separated cleanly, in the agent's words. That, not instability, is why an answer cannot be a gate, and why each declared question needs its own measurement before it reports anything. Storing the answer against a hash of its input is for cost and audit.

A second case from the same repository on 2026-11-17: a plan step said a sample was labelled by hand; a model had labelled it; the box was ticked, and `urzua check` would have passed the original wording. What is left for a judge once the deterministic layer is used was set out by the same repository on 2026-11-17, after it adopted declared checklist items. The checklist settles that every item names evidence, that the evidence resolves and that the status agrees. It cannot settle five things, each of which the repository met or nearly met in its own records: evidence that lives outside the repository and so cannot resolve (a live run's log), where the question is whether the text describes an observation that shows the item was met or only asserts it; evidence that resolves but does not exercise what the item says; an item met by something weaker than its wording; evidence prose that itself says a required thing was not done; and an item that is not checkable at all.

The common shape: the deterministic layer checks that a claim has support attached, and a judge would check that the support is about the claim. The first of the five is narrowed by an evidence form for observations, tracked separately; the rest are candidate questions for a configuration to declare, not questions for the engine to hold. The mission (`ADR-101`) says the tool never judges the change; this proposal has it record another party's judgement, with what was asked and of what, and that boundary needs a decision record before any build. The nearest existing pattern is the reference snapshot: a separate networked command writes a committed file that `check` reads offline.

## Done means

- A decision record decides whether this fits the mission in `ADR-101` and the content-scope ceiling in `SPEC-1`, amending `ADR-101` first if it does not, and is the decision `ADR-93` requires of a command that uses the network. If it is accepted, it fixes that the engine never forms a judgement of its own, that an answer never changes an exit code, that a change to a judge's declaration is a gated change, and what is measured before leaving shadow: for each declared question, its false alarms and misses against cases whose outcome is known. The maintainer accepts it before anything else here is built.
- A configuration can declare a question: its text, its type (yes-or-no first), the event it attaches to (a move into a state, or a field), which parts of the record and of the records it refers to form the input, and the judge to ask. The engine contains no question of its own, shown by a test with a fixture configuration.
- A judge is declared in configuration as data: the protocol it speaks, its address, the model identifier to pin, its input limits and the environment variable holding its credential. The engine implements the common request shape described in Why and reads everything specific to a service from that declaration, so a fourth service that speaks the protocol needs no code; no service's name or address is in the engine, and the engine runs no configuration-declared command. The reference documents the declarations for SubQ Snap, Jev and Levanto Sage, the three the maintainer named on 2026-11-17, shown by a test against a stub server speaking that request shape and by one recorded request and response fixture per documented service, replayed in CI with no network and no credential. A reporting threshold is declared per question and per judge, since a probability from one model is not comparable with another's and one judge's quality differs between questions.
- Asking is a separate command that is never run by `urzua check`; `check` makes no network call and stays repeatable, shown by a test that `check` passes with no network and no credential.
- The answer is written into the record as a claim holding the question, a hash of the exact input sent, the judge and resolved model version, the probability, the date and the commit. The hashed input is a declared canonical form that covers the question text and options and excludes stored answers and the revision log, so storing an answer does not make it stale. While the input hash is unchanged the stored answer is reused and the judge is not asked again; when the input changes the claim is reported stale by the existing staleness machinery, shown by a test of each.
- Nothing leaves the machine unless a configuration declares a judge and a question, shown by a test. A record or a section can be marked as never sent, and the command's dry run prints exactly what would be sent and to which judge without sending it.
- The first delivery is shadow mode for one question declared in a fixture configuration, not in the engine: whether the evidence for a move into a success status shows each checklist item was met. In shadow the answer is kept outside `check`'s report, shown by a test that `check`'s output is identical with and without it. Reporting it as an info-level finding is a later configuration switch, never above info, at a probability threshold the configuration declares.
- The answer is untrusted data and never an approval: record text cannot alter the question, shown by a test with a record that tries to; and a stored answer never satisfies a checklist item, an evidence tier, a computed status or a gate, shown by a test.
- Unreachable, timed out, abstained and over-limit each produce a distinct reported outcome, never a stored answer and never silence; being offline is not a failure of any other command.
- A person can dismiss an answer with an attributed reason that stands until the input changes; a write to a record on a protected path or in a gated status follows the same authority rules as any other write; two branches storing different answers for one input hash merge by a declared rule; and a configuration declares the most calls and input size one run may use, which the dry run prints.
- The reference page states for a reader deciding whether to turn this on: answers can be wrong and may differ between calls, which one service's documentation reports and another's replay did not show; text is sent to a third party; and what each declared judge's retention is remains the adopter's to check.
