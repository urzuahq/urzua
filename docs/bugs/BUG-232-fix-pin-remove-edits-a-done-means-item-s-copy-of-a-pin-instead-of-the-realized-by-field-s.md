# 232 — fix --pin --remove edits a Done-means item's copy of a pin instead of the Realized-by field's

## What was wrong

`apply_remove` in `rust/crates/urzua-core/src/fix/pin.rs` searched the whole body before the revision log for `, <pin>` and then `<pin>, `, and removed every occurrence of the first form it found. On a record that cites the same pin in the `Realized-by` field and in a Done-means item, where the item's copy has the `, <pin>` form and the field's has the `<pin>, ` form (field `X, A`, item `A, X`), `--remove` edited the item and left the field's copy: the command reported the pin removed from the evidence the caller named while the item lost a locator it never named. When the pin had a comma on both sides in the field, the old code stripped the field's copy and the item's alike. It matches on tier, path and hash, so it never touched a different pin. `--replace` is not affected: it rewrites every copy, so field and item move together.

Decision. The maintainer decided on 2026-11-25, in the orchestrating agent's session; the decision is not recorded in the repository or in the pull request, and this bug is where it is written down. The question was whether `urzua fix --pin --remove` should remove only the `Realized-by` copy of a pin that also sits in a Done-means item, leaving the item's copy and saying in the report that it remains. The answer was: "Yes: field copy only". The decision applies when the field holds a copy. So `--remove` edits only the lines of the evidence field, never the body; each item that still cites the pin is listed in the report as `still_cited_by_items` (`{item, line, locator}`). The reason for the difference from `--replace`: removing an item's copy withdraws that item's evidence, which can change the milestone's computed status, so it stays a deliberate edit to that item, while `--replace` moves the evidence and keeps every item citing something. A pin the field does not hold and an item does is removed from the first item that cites it, as before, with the other items listed: the item's copy is then the evidence being withdrawn, and refusing left the `pin-removed` finding naming a command that refused (the class of `BUG-230`).

## Why nothing caught it

No test of `fix --pin --remove` had a record with Done-means items, so the search over the whole evidence text was never run with two copies of one pin in different forms.
