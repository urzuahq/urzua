# 232 — fix --pin --remove edits a Done-means item's copy of a pin instead of the Realized-by field's

## What was wrong

`apply_remove` in `rust/crates/urzua-core/src/fix/pin.rs` searched the whole body before the revision log for `, <pin>` and then `<pin>, `, and removed every occurrence of the first form it found. On a record that cites the same pin in the `Realized-by` field and in a Done-means item, where the item's copy has the `, <pin>` form and the field's has the `<pin>, ` form (field `X, A`, item `A, X`), `--remove` edited the item and left the field's copy: the command reported the pin removed from the evidence the caller named while the item lost a locator it never named. When the pin had a comma on both sides in the field, the old code stripped the field's copy and the item's alike. It matches on tier, path and hash, so it never touched a different pin. `--replace` is not affected: it rewrites every copy, so field and item move together.

Decision. The maintainer decided on 2026-11-25, in the orchestrating agent's session; the decision is not recorded in the repository or in the pull request, and this bug is where it is written down. The question was whether `urzua fix --pin --remove` should remove only the `Realized-by` copy of a pin that also sits in a Done-means item, leaving the item's copy and saying in the report that it remains. The answer was: "Yes: field copy only". So `--remove` edits only the lines of the evidence field, never the body; every item that still cites the pin is named in the report (`still_cited_by_items`); and a pin cited only in items is refused with a message naming the item(s). The reason for the difference from `--replace`: removing an item's copy withdraws that item's evidence, which can change the milestone's computed status, so it stays a deliberate edit to that item, while `--replace` moves the evidence and keeps every item citing something.

## Why nothing caught it

No test of `fix --pin --remove` had a record with Done-means items, so the search over the whole evidence text was never run with two copies of one pin in different forms.

## References

Fixed in `apply_remove`, which now takes the line span of the evidence field (`field_span`) and edits nothing outside it, and in `remove` in `rust/crates/urzua-cli/src/commands/fix_pin.rs`, which refuses a pin that is only in items and reports the items that still cite it. The tests are `fix_pin_remove_edits_the_field_when_the_item_copy_has_the_other_comma_observed_failing` (the `X, A` / `A, X` shape, observed failing before the fix), `fix_pin_remove_refuses_a_pin_cited_only_in_items_observed_failing` (observed failing), `fix_pin_remove_keeps_the_item_copy_of_a_pin_in_the_middle_of_the_field` and `fix_pin_replace_moves_the_field_copy_and_the_item_copy` in `rust/crates/urzua-cli/tests/fix_rebaseline_integration.rs`. The acceptance case `fix-pin-remove-leaves-a-done-means-items-copy-of-the-pin` in `corpus-g` puts the pin only in an item: the old code removed it from the item and applied, the fixed code refuses and names the item, and the case was observed failing before the fix. `SPEC-8` states the behaviour. A removal row also covers a hand removal of the item's copy (`BUG-229`).
