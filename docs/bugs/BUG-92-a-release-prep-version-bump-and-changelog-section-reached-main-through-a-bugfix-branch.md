# 92 — A release-prep version bump and changelog section reached main through a bugfix branch

## What was wrong

`main` carried `version = "0.4.0"` in `rust/Cargo.toml` and a full `## 0.4.0 (2026-09-19)` CHANGELOG
section, 222 lines of it. **No `v0.4.0` tag exists.** The published tags stop at `v0.3.0`.

Both artefacts are generated by the release-prep run and belong on the `release` branch until a
release publishes. They reached `main` through `PR #79` -- *"Round 6: five defects where a check
reported success without looking"* -- whose squash diff is `CHANGELOG.md | 222 +++`,
`rust/Cargo.toml | 2 +-`, changing `version = "0.3.0"` to `"0.4.0"`.

The branch behind it was cut from `release` rather than `main`, after `release` had been merged
forward to pick up an earlier fix, so the prep commit's content was part of its diff against `main`.

**Squash merging is what makes this invisible.** `git merge-base --is-ancestor` reports that the
prep commit `8401d0f` is *not* in `main`'s history -- squash discards the source history and applies
only the flattened content. So the bump is in `main`'s tree while the commit that made it is not in
`main`'s graph, and no amount of reading the history will show where it came from. It is findable only
with `git log -S` over the file.

`PR #72`, the actual release PR, was never merged and did not need to be. The release artefacts
arrived through a bugfix.

The consequence is arithmetic. `knope` computes the next version from the version in the tree, so
from `0.4.0` a patch changeset gives **0.4.1**: the tooling was preparing the release *after* one that
never happened. `PR #72` had silently retitled itself from *"prepare release 0.4.0"* to
*"prepare release 0.4.1"*, and with the consolidated `minor` changeset now pending it would have
computed `0.5.0` -- skipping two versions, one of which contains every change this project has made
since `v0.3.0`.

Reset to `0.3.0`, and the generated CHANGELOG section removed. The real release regenerates it from
`.changeset/`.

## Why nothing caught it

Nothing looks. `make ci` has no reason to compare the in-tree version against the published tags, and
no rule governs the relationship -- the version is not a record and lives outside the corpus the
engine checks.

Two gates saw the PR and neither had reason to object: the `changeset required` check asks only
whether a changeset *exists*, not what else the diff touches, and the review pass did not flag a
bugfix PR bumping the release version.

The retitling of `PR #72` was the only visible symptom, and a title changing quietly on an
already-open PR is not something anyone re-reads. It sat for two days.

The deeper cause is the branch point. Cutting a fix from `release` is indistinguishable from cutting
it from `main` at the moment you do it, and the difference only surfaces at the next release
computation.
