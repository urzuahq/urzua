## urzua harness

This section is written by `urzua harness install` and is rewritten between its markers on every install or update. Do not edit it by hand; change `harness` in `.urzua/config.yaml` instead.

The record-edit guardrails are installed in this repository. What an agent must not do:

- Do not accept or reject a record yourself. Moving a decision record to an accepting status is a person's act. Where the configuration sets `in_session: ask` on the `acceptance` guardrail, your edit that makes such a move prompts the person to approve it, with its receipt; make that edit only when the person asks for the move, and never change a gated status without that answer (not from a shell command, not from a subagent). Never write a receipt row yourself: it records the person's answer to the prompt. When the edit is refused, do what the refusal says.
- Do not set a hook override to get a blocked edit through. A named override is recorded for review; it is the maintainer's to take.
- Do not edit the harness itself: the agent's hook settings, `.git-hooks/`, `.urzua/config.yaml` and the CI workflows are protected paths, and so are the files the harness keeps for itself (`.urzua/cache`, `.urzua/harness.lock`, the override log, the whole git directory `.git` and any `.git` pointer file).
- Write records with their drafting commands and `urzua new`, not by hand; run `urzua check` before committing.

Where `authority` is declared, the engine refuses an agent's Write, Edit, MultiEdit or NotebookEdit, or a file-writing MCP tool, that moves a record to a status a gate names or writes a protected path (a hard link to one included), and no override lifts it; a person edits outside the agent harness. Under `in_session: ask` a move to a gated status is instead put to the person through the agent's permission prompt, and refused where the person cannot be asked. That is the whole claim. Accepted risk, documented by the maintainer on 2026-11-05 and narrowed on 2026-11-06 and 2026-11-07: a shell command that writes a status or edits a guardrail or a file the harness keeps (the post-command check reports it after the command, a gitignored protected file, a record hidden with `git update-index --assume-unchanged` and a commit the same command makes included, when that guardrail is on; it reports a repeat of a change it has already reported only once; nothing stops it), `git commit --no-verify`, a pull request that changes its own workflow, and an agent acting under the maintainer's token (CI proves who authored the pull request, not who decided) all get past it. Do none of these.

The editor hook judges a Write, Edit, MultiEdit or NotebookEdit of a record before it lands. It cannot see a shell command that writes a record, so run `urzua check` after one. Only the verdicts of `urzua harness run` bind; this text is advisory.
